# Reverse-Engineering Web Applications for Autonomous Access
### A Field Report on Methods, Observations, and Reusable Findings

**Abstract.** This report documents a practical investigation into interacting with
modern web applications through their own backend interfaces rather than their user
interfaces. It describes how hidden APIs were located inside single-page applications,
how obfuscated client code was recovered, how request-signing schemes were replicated,
how browser-origin restrictions were navigated, and how the resulting knowledge was
packaged into self-contained, self-healing scripts. The methods are presented generally;
a concrete case study (an in-game gift-code system) is included as an appendix.

---

## 1. Introduction

Web applications increasingly behave as thin clients over private JSON APIs. For both
researchers and automation agents, the practical question is: *what can be learned and
done through those APIs directly?* This report summarizes a repeatable investigation
pattern and the observations that emerged from applying it. No credentials were
obtained or needed; everything described relies on public client resources and the
researcher's own accounts.

## 2. Methodology

The investigation followed a general sequence:

1. **Surface reconnaissance.** Collect structured metadata first: `robots.txt`,
   sitemaps, machine-readable instruction files (e.g., `/llms.txt`), embedded JSON-LD,
   and script/style URLs in the HTML. Structured data often answers half the questions.
2. **Client-code analysis.** Download the JavaScript bundles referenced by the page.
   When bundles are minified or string-obfuscated, recover the string table (decoder
   functions are defined at the top of the file) and enumerate embedded URLs and paths.
3. **Endpoint discovery.** Filter recovered strings for network-shaped literals
   (`/path`, `https://`, `api`, etc.). Where chunks are lazily loaded, resolve chunk
   filenames from the webpack runtime (`js/<name>.<hash>.js`).
4. **Protocol inference.** Examine request construction in the client to learn methods,
   content types, headers, and any signature scheme.
5. **Controlled probing.** Issue low-risk requests (invalid or neutral inputs) to learn
   the server's response semantics before attempting real actions.
6. **Automation and hardening.** Package the working protocol into a dependency-free
   script that can be loaded and executed remotely, with state persistence and
   automatic recovery from predictable changes (e.g., rotated signing keys).

## 3. Findings

### 3.1 Hidden APIs and client-side logic

- Single-page applications reliably disclose their entire API surface in shipped
  JavaScript; the API domain often differs from the page domain.
- Server-side routing details are sometimes visible in error pages: framework-specific
  error documents (e.g., Symfony/PHP "An Error Occurred" pages) reveal the backend stack
  and where method enforcement occurs (application vs. edge).

### 3.2 Obfuscation recovery

- A common obfuscation pattern places all string literals in an array behind a decoder
  function (`decoder(0xNNN)`). The decoder and array are defined at the top of the file;
  evaluating the file in an isolated context (e.g., a Web Worker, which has no DOM)
  makes the decoder callable and the full string table enumerable.
- Plain-text string arrays are also visible directly in the raw bundle, which allows
  targeted regex extraction without executing code.
- Lazy-loaded chunk files follow deterministic naming, letting an agent fetch the
  exact chunk containing the logic of interest.

### 3.3 Request signing

- When clients sign requests, the signing material is necessarily present in the
  client bundle. A typical scheme sorts parameters, serializes them
  (`k=v&k2=v2`, values URL-encoded, objects JSON-encoded), appends a secret, and
  hashes the result (frequently MD5, hex-encoded).
- The scheme can be replicated exactly from the recovered strings. Cryptographic
  implementations should be validated against known test vectors before use.
- Servers distinguish signature failures from other errors, which provides a reliable
  signal for detecting stale credentials or rotated keys.

### 3.4 Browser-origin restrictions and agent access

- Browsers enforce CORS selectively: "simple" requests (GET, and POST with a few
  content types) skip preflight; requests with custom headers or `application/json`
  trigger an `OPTIONS` round-trip that many servers reject.
- A failed cross-origin fetch is not equivalent to a dead endpoint. Responses that
  lack `Access-Control-Allow-Origin` (including error documents) are unreadable to the
  browser even when the server responded. A `mode: 'no-cors'` request can reveal
  whether a server responded at all.
- Several public relays exist that perform the request server-side and return the
  result with permissive CORS:
  - GET-to-any-method converters (e.g., `get2post.vercel.app`), which also serve as
    general GET proxies when `method=GET` is specified. They forward custom headers and
    bodies and return a JSON envelope carrying the upstream status.
  - GET-only CORS proxies (e.g., allorigins variants), which are useful for reading
    pages and static assets.
- Reliability of public relays varies; chaining multiple fallbacks with timeouts is
  markedly more robust than relying on any single one.
- Attempts to reinterpret GET as POST via method-override headers or `_method`
  parameters generally fail when a CDN/WAF enforces HTTP methods before the
  application layer.

### 3.5 Server state semantics and probing

- Servers expose a rich vocabulary of error codes that can be used as ground truth
  before any real operation: invalid identifiers, expired resources, already-consumed
  resources, duplicate claims, rate limits, and authentication failures each tend to
  map to distinct codes.
- Probing with invalid inputs is a low-risk way to map this vocabulary and to
  distinguish "does not exist", "expired", "already used", and "live" states.
- Servers commonly rate-limit silently (on the order of ten requests per minute);
  pacing requests and backing off on explicit rate-limit codes avoids throttling.
- Some requests validate correlated fields (e.g., an account id together with a
  server/region id); the error codes reveal which fields matter.

### 3.6 Automation, state, and resilience

- Dependency-free browser scripts (native `fetch`, `URLSearchParams`, `localStorage`,
  `setTimeout`) run in both browser consoles and modern Node.
- Configuration by opaque identifiers (rather than human-readable names) keeps shared
  artifacts free of personal data.
- Optional derived fields (e.g., a region id implied by an account id) can be resolved
  from public lookups, cached, and only prompted as a last resort.
- Persisting per-identifier results (e.g., in `localStorage`) allows later runs to skip
  work already completed.
- Recovery logic can key off the server's authentication-failure response: re-derive
  the signing secret from the current bundle and retry.
- Remote loading via `fetch(...).then(eval)` has a subtle scoping property: top-level
  function declarations become global, whereas `const`/`let` do not. Attaching an
  explicit global handle (e.g., `globalThis.TOOL = {...}`) makes loaded modules usable.
- Hosting considerations: raw file hosts that send `Access-Control-Allow-Origin: *`
  support `fetch`+`eval`; script-tag loading requires a host that serves a JavaScript
  MIME type.

## 4. Tooling observations

| Tool / approach | Observed behavior |
|---|---|
| Direct `fetch` | Works when the origin serves CORS headers (e.g., raw GitHub, many JSON APIs). |
| GET-to-POST relay (`get2post.vercel.app`) | Converts GET into any method; forwards headers/body; CORS-enabled; also usable as a GET proxy with `method=GET`. Logs requests; strips common secret-like fields from logs. Some bot-protected sites return 403 to it. |
| GET CORS proxies (allorigins, cors-tube) | Reliable for reading pages/assets; occasionally slow or unresponsive. |
| Text readers (`r.jina.ai`) | Useful GET-only fallback. |
| Method-override techniques | Not effective behind method-enforcing edge layers. |

## 5. Limitations, failure modes, and normative considerations

- Public relays and loggers may record request metadata; in this work, payloads sent
  through relays contained no credentials or personal identifiers beyond what was
  needed, and shared artifacts were stripped of personal data.
- The permission surface of these techniques equals that of the application's own UI:
  no authentication was bypassed, and operations were performed only on the
  researcher's own resources.
- Server-side captchas are intended to moderate automated traffic. In the studied
  case the API did not enforce the captcha it presented; the effective constraints were
  therefore request rate and volume, which were kept deliberately conservative.
- Web applications change: endpoints are removed, secrets rotated, and origin
  policies tightened. Findings should be treated as time-sensitive observations, which
  is why recovery mechanisms (re-extraction of keys, fallback relays) matter more than
  any single snapshot.

## 6. Case study: an in-game gift-code system (Kingshot)

*Condensed application of the above. See the hosted artifact for details.*

- **Surface.** The redemption site is a Vue SPA whose bundle is string-obfuscated.
  Recovery of the string table revealed a separate backend API and four endpoints
  (redeem, config, lookup, captcha); two of them (lookup, captcha) were effectively
  unavailable.
- **Signing.** Every request required `MD5(sortedQuery + secret)`; the secret was
  embedded in a lazy-loaded chunk and re-derivable at runtime.
- **Server semantics.** Redemption requests returned a stable set of codes
  distinguishing success, already-claimed, same-type-claimed, expired, unknown,
  exhausted, rate-limited, user-info-mismatch, and signature failure. This made code
  validation and discovery a read-mostly classification exercise.
- **Origins.** The redeem API was reachable cross-origin directly; the account-lookup
  endpoint was not. Account metadata was instead obtained through a fan-site Next.js
  server action relayed through a GET-to-POST converter with an origin header.
- **Artifact.** A single-file, dependency-free script (configured by opaque Player IDs,
  no names) automates kingdom resolution, redemption with pacing/backoff, a live-code
  finder, result persistence, and key self-healing. It is hosted at
  `https://raw.githubusercontent.com/HalitZiyaKARTAL/test19/main/aichats/fastship/js/untested/helpers/game/redeemer2.js`
  and is loadable via `fetch().then(eval)`, after which a `KSR` global handle exposes
  `redeem`, `findCodes`, `findAndRedeem`, `probeCode`, and `ledger`.

## 7. Conclusion

The pattern described — locate the API through client code, replicate its protocol,
probe conservatively to learn semantics, and package the result as a resilient,
self-contained module — generalizes across web applications. Its durability depends
less on any single endpoint or secret and more on recovery paths: runtime re-extraction
of credentials, layered network fallbacks, and state that survives restarts.
