# AI-Agent Web Automation & API Reverse-Engineering — Field Playbook

> **What this is:** a distilled, tool-agnostic playbook for turning a web app into a
> working, self-healing browser script — written from real field work.
> Share it openly, or hand it to a future agent with:
> *"Read this playbook, then do <task> on <target>."*
>
> **Why it exists:** the author spent many tool calls rediscovering these patterns.
> This doc saves the next session (human or AI) from repeating the archaeology.

---

## 1. How to use this doc

- **Any task** that involves: a website with hidden APIs, an SPA, obfuscated JS,
  CORS-blocked endpoints, signing, or building an agent-runnable script.
- Follow phases in order; skip what doesn't apply.
- Each section lists: *what to do*, *why*, *pitfalls*, *worked-example notes*.

**Worked example throughout:** the author used this on the *Kingshot* (Century Games)
gift-code system. The final artifact is referenced in §11. Every "Case:" line is from that job.

## 2. The overall workflow

```
Recon -> Read bundles -> Find APIs -> Understand auth/signing -> Reach them (CORS)
      -> Probe safely -> Classify states -> Automate -> Validate -> Harden (self-heal)
```

Mental rules:
1. **The website is a client.** The real logic is in the network layer it talks to — find that.
2. **Trust the server, not blogs/claims.** Verify everything with real requests.
3. **Prefer read-only probes** while learning; make state-changing calls only when intended.
4. **Build for reuse** — config by identifiers, no hard-coded names/PII, save state.
5. **Assume the target changes** (keys rotate, endpoints die) → build self-healing.

## 3. Phase 1 — Recon & discovery

What to collect first:
- Robots.txt, sitemap.xml, `llms.txt` (LLM-facing docs!), `/.well-known/*`.
- HTML: `<title>`, meta, JSON-LD blocks, embedded JSON (`self.__next_f`, `__NEXT_DATA__`).
- All `<script src>` and `<link>` URLs (these are your entry points to code).
- Obvious API hints in HTML/JS (`/api/`, `graphql`, `fetch(`, `axios`, `baseURL`).

Case notes:
- Kingshot.net exposed an `/llms.txt` (instructions for AI agents) — always check these.
- JSON-LD `ItemList` gave the current "active codes" list — structured data is gold.

Pitfalls:
- Pages may be 100s of KB of RSC payloads — regex targeted chunks, don't eyeball everything.

## 4. Phase 2 — Reading (possibly obfuscated) JS

When bundles are minified **or obfuscated** (hex-string tables, e.g. obfuscator.io):

1. Fetch the bundle(s). Note webpack/Vite patterns:
   - `app.<hash>.js`, lazy chunks `<name>.<hash>.js`; chunk map lives in the main bundle.
2. **Deobfuscate the string table:**
   - Bundles often start with `var X = DECODER; function TABLE(){ return [...strings...] }`
     and code calls `DECODER(0xNNN)`.
   - Extract the decoder name from the first line, `(0,eval)(bundle)` in a **sandbox/worker**,
     then call `DECODER(hexIndex)` to dump strings.
   - String tables are also visible as plain-text arrays in the raw file — grep those.
3. **Find endpoints:** after deobfuscating, filter strings for `/path`, `http`, `.com`, `api`.
4. **Find chunk URLs:** webpack builds `js/<name>.<hash>.js`; `<hash>` may equal the app hash.
5. **Never eval third-party code on a page you care about** — use an isolated Worker
   (no DOM access) or a throwaway context.

Pitfalls:
- Regexes must match actual syntax: `['MD5'])` (there's a `]` before `)`) — check the raw text.
- Obfuscator "rotates" the array at load; only eval the WHOLE file so rotation runs.

## 5. Phase 3 — Understanding auth & signing

Common patterns to detect:
- Plain headers/tokens (Bearer, cookies).
- **Request signing**: client sorts params → builds `k=v&k2=v2` → hashes with a secret →
  sends `sign` + params. The secret is usually **in the client bundle** (it has to be).
- Look for `MD5/HMAC/SHA`, `sort/keys/reduce`, a string appended before hashing.

To replicate:
1. Locate the signer in the bundle (search for `appendSign`, `sign`, `MD5`, `secret`).
2. Re-implement exactly: sort order, encoding (encodeURIComponent vs JSON for objects),
   hash output encoding (hex/base64).
3. **Sanity-check your crypto with known test vectors** before hitting the API:
   `md5('abc') === '900150983cd24fb0b6963f7d28e17f72'` (use a second source to confirm).

Case notes:
- Secret was at hex index `0x1b4` of a lazy chunk, used as `MD5(sortedQuery + secret)`.
- Wrong/old key → server replied `Sign Error` with `err_code: 0` — that signature became
  the **detector** that triggers automatic re-extraction.

Pitfalls:
- Signing is "security by obscurity": still handle rotation gracefully.
- Some servers validate extra fields (e.g., a kingdom id tied to a player id) → learn
  which fields are validated by testing with safe probes and reading error codes.

## 6. Phase 4 — Network access & CORS from agents

### Know the CORS rules that matter
- **Simple requests** (GET, or POST with `application/x-www-form-urlencoded`,
  `multipart/form-data`, or `text/plain`) skip preflight → work cross-origin if the server
  sends `Access-Control-Allow-Origin` (often `*`) on the response.
- **Preflighted requests** (custom headers like `X-...`, `Content-Type: application/json`)
  need an `OPTIONS` round-trip; many servers/WAFs reject `OPTIONS`.
- **CORS ≠ endpoint dead.** A "Failed to fetch" can mean the response is an error page
  *without* ACAO headers. Diagnose with a `mode:'no-cors'` fetch (tells you the server
  responded at all) or a server-side relay.

### Toolbox (all verified to exist/work, Sept 2026)
| Tool | What it does | Notes |
|---|---|---|
| `get2post.vercel.app` | GET→POST converter; **also a general CORS proxy** | `/api/post?url=<t>&method=GET&response=json` for GET (default is POST!). Forwards custom headers/body. JSON envelope `{status, headers, body}`. Logs requests; redacts secrets. ~1 MiB cap. Some origins (bot-protected sites) return 403. |
| `api.allorigins.win/raw?url=` & `allorigins.hexlet.app/raw?url=` | GET CORS proxy | Reliable; sometimes slow/hangs — use timeouts + fallbacks. |
| `cors-tube.vercel.app/?url=` | GET CORS proxy | Worked as fallback. |
| `r.jina.ai/<url>` | GET text reader | Readable fallback; GET only. |
| direct `fetch` | best when ACAO present | raw.githubusercontent, many JSON APIs allow `*`. |
| `X-HTTP-Method-Override` / `_method` | GET-as-POST trick | **Usually fails**: WAF/CDN enforces methods before the app. Test once, don't insist. |

### Building robust fetch helpers
```
try direct -> try get2post (with method/data/headers) -> try GET proxies -> throw
```
- Always **parse the relay envelope** and treat non-2xx upstream as failure.
- Add **timeouts/AbortController** — public proxies hang often.
- For server-actions/CSRF-protected endpoints, spoofing `Origin` through a relay can work
  (the relay sends your headers upstream).

## 7. Phase 5 — Probing safely & classifying states

- **Read-only probes first:** call endpoints with fake/neutral inputs to learn response codes
  (e.g., an invalid id/code) — cheap and harmless.
- **Map the verdict space** into a table: success vs already-done vs expired vs not-found vs
  rate-limited vs auth/sign error. These become your "ground truth".
- **Idempotency:** if re-sending a state-changing call is safe (server says "already done"),
  you can retry to learn state — but never retry blindly on timeouts that may have succeeded.
- **Rate limits:** servers often allow ~10/min silently. Pace ≥4s, back off 60s on the
  rate-limit code, and keep per-IP volume low. Look for `x-ratelimit-*` headers.

Case notes:
- Probing an unknown code with a fake captcha revealed live/expired/fake instantly via
  server codes (SUCCESS / TIME ERROR / CDK NOT FOUND / SAME TYPE...). This turned
  "find codes" into a cheap classification loop.

## 8. Phase 6 — Building reusable, agent-runnable scripts

Design goals:
1. **Config = identifiers only** (IDs/keys), never names/PII as magic values.
   If names exist in data, parse-and-discard; don't hardcode.
2. **Vanilla JS, zero deps**: `fetch`, `URLSearchParams`, `setTimeout`, `localStorage`.
   Works in browser console and Node 18+.
3. **Auto-resolve optional fields** (e.g., look up a related id from an API/proxy),
   with a cached/built-in fallback and a one-time prompt — then remember.
4. **Save state** (ledger) keyed by identifiers in `localStorage`; skip already-done work.
5. **Self-heal**: detect auth/sign/key failures by response signature → re-derive the secret
   from the live bundle → retry.
6. **Pace & backoff** built in.
7. **Expose a global handle** (`globalThis.TOOL = { ... }`).

### Critical JS gotcha for `fetch().then(eval)` loading
- In classic `<script src>`, top-level `const/let` become global → call directly.
- Via **eval**, top-level `function` declarations leak but `const`/`let` do **NOT**.
  → Always attach a `globalThis` handle (e.g., `KSR`) so callers can reach everything.
- Workers lack `localStorage`/`prompt`/`document` — degrade gracefully or run on main thread.

### Hosting for agents
- Raw GitHub (`raw.githubusercontent.com`) is CORS-open (`*`) → `fetch().then(eval)` works.
- But `raw.githubusercontent` serves `text/plain` → **blocked in `<script src>`**.
  Use GitHub Pages / a JS-MIME host for script-tag loading.
- Keep URLs stable (don't leave files under `untested/` forever).

## 9. Phase 7 — Validation before you trust it

1. Crypto test vectors (§5).
2. **Mocked E2E**: override `fetch` with a fake router; run the whole flow; assert state
   (ledger writes, skip logic, parsing).
3. **Live smoke test**: one harmless real call (fake id/code) → expect the "not found" verdict.
   That proves the full chain (lookup → signing → POST → parse) without side effects.
4. Then, and only then, run real actions.

## 10. Universal gotchas & lessons

- **Don't trust third-party "status/active list" claims** — verify with the server.
- **CORS ≠ blocked** (§6). Always distinguish preflight failure vs missing ACAO vs dead route.
- **Public proxies are flaky** — timeouts + fallback chains, never single-proxy.
- **Method override usually dies at the WAF** — don't burn time.
- **Read error pages**: "405 Method Not Allowed"/"404 Not Found" style pages reveal the
  framework (Symfony/PHP etc.) and where routing happens.
- **Eval third-party code only in sandboxes**; use workers to read obfuscated bundles.
- **Regex against minified code**: account for real syntax (`['MD5'])` etc.).
- **Check for `/llms.txt`** and structured data (JSON-LD) first — they can answer half the task.
- **Rate etiquette protects you**: aggressive probing gets IPs throttled/blocked.
- **Only act on your own accounts/data**, and never share other people's identifiers.

## 11. Worked example (Kingshot gift codes) — condensed

Target: redeem game gift codes on several own accounts, find live codes, keep tool alive.
Outcome: full self-contained script, live-tested.

Repo file:
`https://raw.githubusercontent.com/HalitZiyaKARTAL/test19/main/aichats/fastship/js/untested/helpers/game/redeemer2.js`

Load & run:
```javascript
fetch('<raw url above>').then(r=>r.text()).then(eval).then(()=>KSR.findAndRedeem())
```
Highlights that map to this playbook:
- Obfuscated Vue bundle → deobfuscated string tables → found API base + endpoints.
- Signing = `MD5(sortedQuery + secret)`; secret re-extractable from chunk (§5).
- Server doesn't enforce captcha; `kid`+`fid` validated; verdict table §7 drove everything.
- `/player` dead → kingdom lookup via fan-site Next.js server action relayed by get2post (§6).
- Script: IDs-only config, ledger, 4s pacing + 60s backoff, key self-heal, finder.
- Results (Sept 2026): 4 live codes found/verified; 8 successful redemptions across accounts.

## 12. Ethics & safety summary

- Automate only what the site's own UI does, on resources you own/are authorized for.
- Captchas exist to slow bots; a server not enforcing them doesn't make spam okay.
- Relays/loggers may record requests — send no secrets; prefer throwaway/redacted data.
- Don't publish others' Player IDs/emails/keys. Strip PII from shared artifacts.
